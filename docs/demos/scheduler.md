# Планировщик погоды в двух терминалах

Цель: показать, что worker в терминале A периодически опрашивает Open‑Meteo и сам печатает сводку модели, а
расписание создаётся и читается из терминала B через `ask` без запущенного worker. Состояние хранится
в `.local/scheduler.sqlite` и `.local/reports/` (каталог `.local/` не попадает в Git).

## Требования

- Node 24, `npm ci`, корневой `.env` с `LAB_LLM_API_KEY` (нужен только для `scheduler run` и `ask`);
- сеть для DeepSeek и Open‑Meteo, API-ключ Open‑Meteo не требуется;
- команды выполняются из корня репозитория.

## Про интервал 10 секунд

Опрос каждые 10 секунд служит показу планировщика: [Open‑Meteo](https://open-meteo.com/en/docs) строит текущие
условия по 15-минутным модельным данным, поэтому несколько ответов подряд относятся к одному наблюдению. Worker
сохраняет каждый запрос, но в сводке считает запросы и уникальные наблюдения отдельно. Для постоянного сбора
разумен интервал около 15 минут (`collectEverySeconds: 900`).

## Терминал A: worker

```sh
npm run dev -- scheduler run
```

Команда занимает терминал до Ctrl+C. Ожидаемое начало вывода:

```text
Планировщик запущен, база: /…/.local/scheduler.sqlite. Остановка — Ctrl+C.
```

## Терминал B: расписание через `ask`

```sh
npm run dev -- ask "Проверяй погоду в Новосибирске каждые 10 секунд, выводи сводку раз в минуту"
```

Перед ответом печатается `MCP: schedule_weather — выполнено`; ответ модели содержит ID расписания (`sch_` и 8
hex-символов) и время первого опроса и первой сводки. Первый опрос — через 10 секунд после создания, первая
сводка — через минуту.

## Сводка в терминале A

Через минуту после создания расписания в терминале A без новой реплики появляется блок:

```text
── Сводка · Новосибирск ──

---
scheduleId: sch_5c3fe18d
city: Новосибирск
periodStart: 2026-09-23T08:19:21Z
periodEnd: 2026-09-24T08:19:21Z
generatedAt: 2026-09-24T08:19:23Z
requests: 6
succeeded: 6
failed: 0
uniqueObservations: 1
---

# Сводка погоды: Новосибирск

Период (UTC): 2026-09-23T08:19:21Z — 2026-09-24T08:19:21Z
Уникальных наблюдений: 1

<текст модели: изменение температуры, минимум, максимум, среднее, число запросов и ошибок>
```

Frontmatter и заголовок добавляет host; две строки «Период» и «Уникальных наблюдений» модель обязана вернуть
дословно, host сверяет их с рассчитанными значениями. Сводка печатается только после того, как сервер
подтвердил сохранение.

## Чтение сводки

```sh
npm run dev -- scheduler summary Новосибирск
npm run dev -- scheduler summary sch_5c3fe18d
npm run dev -- ask "Какая последняя сводка по погоде в Новосибирске?"
```

Город можно указывать без страны: расписание «Новосибирск, Россия» находится и по «Новосибирск». Если совпадений
нет, ответ перечисляет существующие расписания с ID.

`scheduler summary` читает сохранённый текст через MCP и не обращается к модели: работает без
`LAB_LLM_API_KEY` и при остановленном worker. Если городу соответствуют несколько расписаний, команда
перечисляет их ID. `ask` вызывает модель для выбора инструмента и ответа (`MCP: get_weather_summary —
выполнено`), но сводку заново не генерирует.

## Остановка, перезапуск и второй worker

Ctrl+C в терминале A прекращает запуск новых операций, даёт текущему опросу или генерации завершиться,
сохраняет результат и закрывает соединения (`Планировщик остановлен.`). Повторный `scheduler run` продолжает
расписания: просроченные опрос и сводка выполняются по одному разу, пропущенные периоды не превращаются в
измерения. Второй `scheduler run` для той же базы завершается сообщением
`Ошибка · Планировщик уже запущен для этой базы.`; после остановки или аварийного завершения первого worker
запускается снова без ручных действий.

«24/7» здесь — пока открыт терминал и работает Mac. После закрытия терминала или перезагрузки worker запускают
вручную; `launchd` и другие способы автозапуска не используются.

## Отмена расписания

```sh
npm run dev -- ask "Отмени расписание погоды sch_5c3fe18d"
```

Будущие запуски прекращаются, история опросов и последняя сводка остаются доступными.

## Сброс состояния

Только после остановки worker и других процессов, использующих базу, из корня репозитория:

```sh
rm -f -- .local/scheduler.sqlite .local/scheduler.sqlite-wal .local/scheduler.sqlite-shm
```

Команда удаляет расписания, опросы и тексты сводок. Файлы в `.local/reports/` остаются на диске, но после
сброса не возвращаются как актуальные: источник для чтения — SQLite. Следующий `scheduler run` создаёт пустую базу.

## Что проверено

**Автоматические тесты** (без внешних API и ключа): шесть опросов за минуту при 10/60 секундах и один вызов модели;
дедупликация по времени наблюдения; отказ при неверных ответах модели; восстановление `.md` из SQLite; Ctrl+C во
время операции; отказ второго worker и восстановление после `SIGKILL`; публичный режим без служебных операций; полный
сценарий терминалов A и B на настоящих процессах сервера с подменёнными погодой, моделью и часами
(`apps/host/src/app/tests/scheduler.test.ts`).

**Ручной запуск 24.09.2026** с настоящим DeepSeek (`deepseek-flash`) и Open‑Meteo, база во временном каталоге:
`ask` создал расписание вызовом `schedule_weather`; worker через минуту напечатал сводку с `requests: 6`,
`uniqueObservations: 1` (все шесть ответов относились к одному 15-минутному наблюдению); SIGINT группе процессов
завершил worker с сообщением об остановке, без оставшихся процессов и `-wal`-файлов; повторный запуск возобновил
расписание (число запросов выросло без «догоняющих» опросов); `scheduler summary` в пустом окружении из другого
каталога вернул тот же текст; `ask` прочитал сводку (`get_weather_summary`) и отменил расписание
(`cancel_weather_schedule`). Температуры и формулировки модели меняются между запусками и не гарантируются.

## Ограничения

Сводка и опросы выполняются одним последовательным циклом: на время генерации следующие опросы ждут. Нет
переподключения к упавшему серверу, автозапуска и очистки истории. За сутки при интервале 10 секунд для сводки
читается до 8 640 строк.
