# Проверка обновления npm-зависимости host

Цель: показать, что агент сам проходит цепочку из пяти MCP-вызовов через три сервера (Filesystem,
npm-registry, github-releases) без гарантированного порядка от host, и печатает статусные строки по
факту вызова, а не по сценарию. Решение — [ADR 0007](../adr/0007-orchestration-mcp.md).

## Требования

- установленные зависимости (`npm ci`);
- `LAB_LLM_API_KEY` в окружении или корневом `.env`;
- сеть для DeepSeek, npm registry и GitHub REST API. Ключи npm и GitHub не нужны — `github-releases`
  работает без токена, лимит без токена — 60 запросов в час на IP.

## Основной сценарий

Из корня репозитория:

```sh
npm run dev -- ask "Проверь, стоит ли обновить Zod в apps/host/package.json, и сохрани короткий отчёт"
```

Ожидаемые пять строк статуса перед ответом, в этом порядке:

```text
MCP: filesystem › read_text_file — выполнено
MCP: npm-registry › get_npm_package — выполнено
MCP: github-releases › list_github_releases — выполнено
MCP: github-releases › get_github_release — выполнено
MCP: filesystem › write_file — выполнено
```

Затем ответ агента с текущей и последней версией, ссылкой на релиз GitHub, кратким пересказом изменений и
путём сохранённого отчёта. Проверить отчёт:

```sh
cat .local/reports/dependency-zod.md
```

## Нерелевантный вопрос

```sh
npm run dev -- ask "Какая погода в Омске?"
```

Модель вызывает только `get_current_weather`; печатается одна строка:

```text
MCP: open-meteo › get_current_weather — выполнено
```

Инструменты Filesystem, npm-registry и github-releases не вызываются, хотя их сессии всё равно открыты и
закрыты (`ask` всегда поднимает все пять сессий, чтобы собрать общий список инструментов для модели).

## Сценарий ошибки: пакета нет в манифесте

```sh
npm run dev -- ask "Проверь, стоит ли обновить left-pad в apps/host/package.json"
```

Модель читает манифест, не находит `left-pad` и останавливается сама, не вызывая остальные инструменты —
печатается только одна строка:

```text
MCP: filesystem › read_text_file — выполнено
```

Ответ называет причину и не выдумывает версию несуществующей в манифесте зависимости.

## Что не входит в это демо

Автоматические тесты (`apps/host/src/app/tests/orchestration.test.ts`,
`orchestrationLimits.test.ts`, `dependencyFiles.integration.test.ts`) проверяют механику при заданном
выборе модели — fake-модель детерминированно выбирает инструменты, но реальные тексты и порядок
рассуждений DeepSeek не фиксируются как тестовый ожидаемый результат. Только это демо использует
настоящие DeepSeek, npm registry и GitHub API.

## Подтверждение

Все три сценария выше выполнены вручную 2026-09-28 с настоящими DeepSeek (`deepseek-flash`), npm registry
и GitHub API. Основной сценарий: пять строк `MCP:` в указанном порядке, ответ агента подтвердил
`4.5.4 → 4.6.5` со ссылкой на `https://github.com/colinhacks/zod/releases/tag/v4.6.5` и сохранил
`.local/reports/dependency-zod.md` с разделами «Изменения» и «Рекомендация». Нерелевантный вопрос дал
ровно одну строку `MCP: open-meteo › get_current_weather — выполнено`. Сценарий отсутствующего в манифесте
пакета (`left-pad`) дал ровно одну строку `MCP: filesystem › read_text_file — выполнено` и ответ без
вызова npm-registry и github-releases.

Точный порядок аргументов, формулировки ответа и содержимое отчёта — выбор конкретного запуска модели, а
не гарантированный результат: DeepSeek мог бы, например, сначала уточнить версию у пользователя или
пропустить поиск релиза GitHub, если бы npm не сообщил репозиторий. Если в следующем запуске модель
выбрала другой порядок или пропустила шаг, это не ошибка host — сначала проверьте `prompts/
dependencyTools.md`, а не подгоняйте это демо под другой вывод.
