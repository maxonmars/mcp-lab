# 0007 — Orchestration MCP: несколько раундов и серверов за одну реплику

Статус: принято для задания дня 19.
Дата: 2026-09-28.

## Цель и минимальный результат

Агент сам выбирает инструменты нескольких MCP-серверов и маршрутизирует вызовы вместо одного гарантированного
tool call за реплику. Сценарий проверки: пользователь пишет в `ask` «Проверь, стоит ли обновить Zod в
apps/host/package.json, и сохрани короткий отчёт», а агент самостоятельно проходит цепочку из пяти вызовов
через три разных MCP-сервера — читает манифест host через Filesystem MCP, узнаёт последнюю версию пакета
через новый сервер `npm-registry`, находит подходящий релиз GitHub через новый сервер `github-releases` и
сохраняет отчёт обратно через Filesystem MCP — и отвечает с указанием сохранённого пути. Перед ответом
печатаются пять строк `MCP: <сервер> › <инструмент> — выполнено`.

## Рассмотренные варианты

- Фасад-пайплайн, как в `outfit` (ADR 0005): один вызов host выполняет всю цепочку сам. Отклонено — здесь
  порядок и состав шагов должна выбирать модель (GitHub может отсутствовать, отчёт может быть не нужен),
  а не быть жёстко зашитым host.
- Сырые инструменты Filesystem (`read_text_file`, `write_file` и другие) видны модели напрямую. Отклонено —
  путь к манифесту и каталог отчётов должны быть фиксированными, а не аргументами, которые придумывает модель.
- Многораундовый `Agent` с настраиваемым лимитом вызовов: каждый ответ модели проверяется целиком до
  исполнения, вызовы одного ответа исполняются по порядку, раунды продолжаются, пока не исчерпан лимит.
  Принято.

## Решение

- `Agent` принимает `AgentOptions.maxToolCalls` (по умолчанию 1, как раньше). `respond()` — цикл: строит
  запрос с `toolChoice: "auto"`, пока не исчерпан лимит, иначе `"none"`; для ответа `tool_calls` проверяет
  весь список вызовов (число, лимит, известность каждого инструмента, форму аргументов каждого) **до** первого
  исполнения и исполняет их строго по порядку, без параллелизма — источник инструментов делит один
  MCP-транспорт на сервер. При `max = 1` поведение прежнее, кроме одного случая: два вызова в одном ответе
  теперь дают `TOOL_CALL_LIMIT_EXCEEDED`, а не `INVALID_TOOL_CALL_COUNT` (эта ошибка остаётся только для нуля
  вызовов). `ask` использует `ASK_MAX_TOOL_CALLS = 6`; фоновый `dailyAgent` планировщика и фасад `outfit`
  остаются с лимитом по умолчанию.
- Два новых самостоятельных MCP-сервера, по образцу `open-meteo`: `servers/npm-registry` (`get_npm_package` —
  последняя версия, описание, лицензия, домашняя страница и репозиторий GitHub публичного npm registry) и
  `servers/github-releases` (`list_github_releases`, `get_github_release` — список и заметки релизов
  публичного GitHub REST API без токена). Оба входят в `ask` и не используются другими командами.
- Новая фича host `features/dependencies` — проекция Filesystem MCP с двумя фасадами: `read_host_manifest`
  (без аргументов, путь host задаёт сам) и `save_dependency_report` (принимает только `packageName` и
  `markdown`, путь в `.local/reports` вычисляет host). Сырые `read_text_file`/`write_file` и остальные
  инструменты Filesystem модели не видны.
- Каждый MCP-источник, который `ask` передаёт `Agent`, несёт метку `serverName` (`StdioToolSourceOptions`).
  `McpToolSourceError` хранит `server` как обязательное поле; CLI подставляет его в текст ошибки вида
  «MCP-сервер «x»…», а строка статуса — `MCP: <server> › <tool> — выполнено|ошибка` (заменяет формат
  `MCP: <tool> — …` из ADR 0003, где сервер был только один).
- `ask` открывает сессии всех пяти серверов (Open‑Meteo, scheduler, filesystem, npm-registry,
  github-releases) вложенно, одну на реплику, и объединяет их проекции `combineToolSources`; каталог
  `.local/reports` создаётся до открытия сессий, потому что Filesystem-сервер при старте отбрасывает
  несуществующие каталоги из списка разрешённых.

## Последствия

Каждый `ask` теперь запускает до пяти дочерних MCP-процессов вместо двух, даже если модель использует лишь
часть инструментов. `github-releases` работает без токена: лимит — 60 запросов в час на IP, что подходит
для учебного использования, но не для интенсивного. Обновление зависимости не выполняется — только отчёт;
`package.json` и `package-lock.json` не изменяются. Профиль, история проверок и кэш ответов не добавляются.

## Проверка

`core/tests/agentRounds.test.ts` — несколько раундов до лимита, несколько вызовов одного ответа по порядку,
отказ неизвестного инструмента и некорректных аргументов до исполнения, превышение лимита, `isError`
продолжает цикл, конструктор отклоняет некорректный `maxToolCalls`. Тесты серверов — офлайн на подменённом
`fetch` и протокольные на `InMemoryTransport`. `features/dependencies/tests/files.test.ts` — проекция на
fake `ToolSource`. `app/tests/orchestration.test.ts` и `orchestrationLimits.test.ts` — полный сценарий на
fake-сессиях всех пяти серверов с fake-моделью, которая извлекает аргументы каждого следующего вызова из
текстов предыдущих ответов (а не по фиксированному сценарию), лимит вызовов, отказ на неизвестном
инструменте и `isError` от GitHub. `app/tests/dependencyFiles.integration.test.ts` — та же проекция поверх
настоящего Filesystem-сервера. Ручное демо — [docs/demos/orchestration.md](../demos/orchestration.md).
