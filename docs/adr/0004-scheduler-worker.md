# 0004 — Планировщик с worker в host

Статус: принято и реализовано в первой версии.
Дата: 2026-09-24.

## Контекст

Учебная цель — создать расписание через MCP, выполнить периодическую работу без новой реплики
пользователя и получить накопленную сводку. Текущий host закрывает MCP-соединение после каждого
`ask`, поэтому таймер в запущенном на время реплики stdio-сервере не выполняет фоновые задания.

Минимальный результат — периодический сбор погоды через Open‑Meteo MCP, сохранение каждого опроса
и независимая публикация короткой сводки, написанной моделью по накопленным данным за 24 часа.

## Варианты

- Таймер внутри краткой MCP-сессии прекращает работу после `ask`.
- Worker внутри MCP-сервера потребовал бы доступа сервера к модели и отдельного LLM-адаптера.
- Worker в host использует существующий `ModelPort`; MCP-сервер планировщика владеет состоянием.

## Решение

- `apps/host/src/features/scheduler` содержит фоновый цикл, расчёт показателей и инструкцию модели
  в `prompts/weatherSummary.md`. `app/compose.ts` передаёт фиче MCP-клиенты, `ModelPort`, часы,
  настройку и вывод. Фича не импортирует соседнюю MCP-фичу или исходники серверов.
- `servers/scheduler` владеет расписаниями, результатами опросов и опубликованными сводками.
  Публичные MCP-инструменты отделены от служебных операций worker двумя режимами регистрации
  stdio-сервера. Host работает с состоянием через MCP и не открывает SQLite напрямую.
- MCP-инструменты первой версии: `schedule_weather`, `get_weather_summary` и
  `cancel_weather_schedule`. Создание принимает город, `collectEverySeconds` и
  `summaryEverySeconds`, возвращает ID и время следующего опроса и публикации. Интервалы независимы:
  например, опрос каждые 10 секунд и сводка каждую минуту.
- Служебные MCP-операции позволяют worker получить просроченные задания, записать опрос, прочитать
  накопленные результаты и сохранить созданную моделью сводку. Эти операции не передаются Agent.
- Host соединяет публичный scheduler и Open‑Meteo как источники инструментов для `ask`, сохраняя
  один tool call за реплику и текущий контракт `ToolSource`. Worker читает структурированный
  результат Open‑Meteo напрямую через MCP: текущий `ToolSource` передаёт только текст.
- Для точной дедупликации Open‑Meteo MCP добавляет UTC-время наблюдения в структурированный
  результат. Сейчас он передаёт только локальное `observedAt` без UTC-смещения.
- `scheduler.dbPath` регистрируется в `app/settings.ts` с исходным значением
  `.local/scheduler.sqlite`, `scheduler.reportsDir` — со значением `.local/reports`. Host передаёт
  MCP-серверу абсолютные пути.
- `scheduler run` и `scheduler summary <город|ID>` регистрируются в `app/commands.ts` для CLI и REPL.
  Первая команда запускает цикл в текущем процессе host и не возвращается до его остановки;
  вторая читает опубликованный текст через MCP без вызова модели. Для `scheduler run` нужен
  `LAB_LLM_API_KEY` из окружения.

## Работа и остановка

- Worker остаётся активным, пока работает процесс host и Mac не выключен. После закрытия терминала
  или перезагрузки его запускают вручную той же командой `scheduler run`.
- На каждом сроке сбора worker вызывает `get_current_weather` через MCP и передаёт серверу
  планировщика успешный результат либо точную причину ошибки. Каждый запрос сохраняется в SQLite;
  модель на этом шаге не вызывается.
- На каждом отдельном сроке сводки worker получает завершённые записи за последние 24 часа и
  рассчитывает число запросов, успешных и ошибочных запусков, число уникальных наблюдений,
  изменение температуры, минимум, максимум и среднюю по уникальным наблюдениям. Модели передаётся
  краткий Markdown-контекст с этими фактами и ограниченным набором наблюдений, без сырых JSON-дампов.
- Host вызывает `ModelPort.complete()` один раз на срок сводки с `tools: []` и `toolChoice: "none"`. Модель
  пишет содержательную часть отчёта с периодом и числом уникальных наблюдений; host проверяет их
  по рассчитанным данным и добавляет в заголовок и YAML frontmatter. Текст модели входит в отчёт.
- Host передаёт готовый Markdown серверу планировщика. Сервер сохраняет его в SQLite и атомарно
  заменяет `.local/reports/<schedule-id>.md`; после подтверждения host автоматически печатает
  сводку в терминале A. Если ответ модели некорректен или сохранение не сработало, последняя сводка
  остаётся доступной, ошибка фиксируется, а следующий срок публикации обрабатывается отдельно. SQLite —
  источник сохранённого текста; отсутствующий Markdown-файл восстанавливается из него.
- Расписания, сроки следующего опроса и публикации, результаты и опубликованный текст сохраняются
  в `.local/scheduler.sqlite`. Следующий `scheduler run` возобновляет оба расписания. После простоя
  просроченный опрос выполняется один раз; пропущенные интервалы не подменяются историческими
  измерениями. Просроченная публикация также выполняется один раз.
- Ctrl+C прекращает запуск новых заданий. Текущий опрос или генерация завершаются в пределах своих
  таймаутов, запись фиксируется, MCP-сессии закрываются, сервер закрывает SQLite.
- Для одной базы допускается один worker. Второй `scheduler run` завершится до начала работы с
  сообщением «Планировщик уже запущен для этой базы».
- `get_weather_summary` возвращает последнюю опубликованную сводку по ID или городу, не вызывая
  `ModelPort`. Если городу соответствуют несколько расписаний, инструмент возвращает их ID.

## Повторные наблюдения

[Open‑Meteo](https://open-meteo.com/en/docs) указывает, что текущие условия основаны на
15-минутных модельных данных. Интервал 10 секунд служит демонстрации планировщика; для длительного
сбора погоды разумный начальный интервал — около 15 минут.

Каждый запрос остаётся отдельной записью в SQLite. Уникальный временной слот определяется парой
`(scheduleId, observedAtUtc)`; если несколько ответов относятся к одному слоту, в расчёте
температуры используется последний. Число запросов и число уникальных наблюдений показываются
отдельно. Изменение и средняя температура считаются только по уникальным слотам. Географическая
точка фиксируется по первому успешному ответу; другой результат геокодирования для того же
расписания отмечается ошибкой и не включается в агрегат.

## Последствия

Пока `scheduler run` занимает терминал A, запросы `ask` выполняются в терминале B. Через `ask`
можно создать расписание и позже спросить о последней сводке, даже если вывод в терминале A был
пропущен. Обычный `ask` вызывает модель для выбора MCP-инструмента и финального ответа, но не
генерирует сводку заново. Команда `scheduler summary <город|ID>` возвращает тот же сохранённый
текст без обращения к модели. Чтение возможно и при остановленном worker. Выполнение расписаний
приостанавливается, когда worker не работает.
Проверка единственного worker не должна мешать повторному запуску после штатного или аварийного
завершения процесса.

## Реализация

- Право worker занимает операция `worker_start`, а не запуск процесса: клиент MCP в режиме `auto` сначала
  запускает пробный процесс сервера. Блокировка — эксклюзивная транзакция SQLite на файле `<база>.lock`
  рядом с базой; ОС снимает её при любом завершении процесса, поэтому устаревших блокировок нет.
- Ctrl+C приходит всей группе процессов терминала, а `npm run` пересылает его повторно. Серверы worker
  запускаются с `--ignore-sigint` и завершаются по закрытию stdin; `app/main.ts` считает повторные сигналы в
  течение секунды одним, а более поздний повторный — принудительным выходом.
- Следующий срок после запуска: при опоздании не больше секунды — по сетке (`срок + интервал`), иначе, после
  простоя, — от фактического запуска. Ошибка публикации тоже сдвигает срок публикации.
- Чтение по городу: точное совпадение строки, иначе совпадение названия без уточнения после запятой или имени
  места Open‑Meteo; при отсутствии совпадений ответ перечисляет существующие расписания.
- Допустимые интервалы: опрос 5–86 400 секунд, сводка 10–86 400 секунд.
- Опросы и сводки выполняет один последовательный цикл: на время генерации следующие опросы ждут.
- Строки с периодом и числом наблюдений модель возвращает дословно; допускается обычная Markdown-разметка вокруг них.

## Очистка SQLite

После остановки worker и завершения других процессов, использующих эту базу, из корня репозитория:

```sh
rm -f -- .local/scheduler.sqlite .local/scheduler.sqlite-wal .local/scheduler.sqlite-shm
```

Команда удаляет расписания, результаты опросов и сохранённые тексты сводок. Markdown-файлы в
`.local/reports/` остаются на диске; после сброса базы они не считаются актуальными и не
возвращаются MCP-инструментом.
Следующий `scheduler run` создаст пустую базу.
При WAL-режиме файлы `-wal` и `-shm` могут оставаться после аварийного завершения; их удаляют
только вместе с базой и только после закрытия всех подключений
([SQLite WAL](https://www.sqlite.org/wal.html#the_wal_file)).

## Проверка

Тесты с подменёнными часами, MCP-клиентом и fake `ModelPort` проверяют: за минуту с интервалами
10/60 секунд выполняются опросы и один вызов модели; её запрос содержит накопленные данные и
рассчитанные показатели; её ответ входит в отчёт с периодом и числом уникальных наблюдений.
Отчёт сохраняется в SQLite и Markdown, автоматически появляется в терминале A без пользовательской
реплики и доступен после перезапуска. Прямое чтение через MCP и `scheduler summary` не вызывает
модель; пустой ответ или неверные период и число наблюдений не заменяют последнюю сводку. Также
проверяются дедупликация, Ctrl+C во время записи, отказ второго worker и протокольные границы
публичных и служебных операций.
Ручное демо с DeepSeek показывает `scheduler run` и `ask` в двух терминалах
([docs/demos/scheduler.md](../demos/scheduler.md)); его результат отделён от автоматических тестов.
`npm run check` проходит без изменения границ core.
