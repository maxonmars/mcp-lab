# scheduler MCP server

## Назначение

Самостоятельный MCP-сервер, который владеет состоянием планировщика погоды: расписаниями, результатами
каждого опроса и опубликованными сводками. Сам он ничего не опрашивает и не обращается к модели: опрос
Open‑Meteo и генерацию текста выполняет worker в процессе host (`scheduler run`), а сервер принимает
результаты и отдаёт сохранённое. Решение и границы — в [ADR 0004](../../docs/adr/0004-scheduler-worker.md).

## Два режима регистрации

Один и тот же процесс запускается в одном из режимов; список инструментов режима — весь его контракт.

| Режим | Запуск | Инструменты |
|---|---|---|
| публичный | без флагов | `schedule_weather`, `get_weather_summary`, `cancel_weather_schedule` |
| worker | `--worker` | `worker_start`, `worker_get_due`, `worker_record_poll`, `worker_get_history`, `worker_publish_summary`, `worker_record_summary_failure` |

Обязательные аргументы: `--db <абсолютный путь к SQLite>` и `--reports-dir <абсолютный каталог>`.
Необязательный `--ignore-sigint` нужен процессу, которым владеет worker: Ctrl+C приходит всей группе
процессов терминала, а сервер должен успеть записать текущий результат и завершиться по закрытию stdin.

### Публичные инструменты

- `schedule_weather` — `city` (2–100 символов), `collectEverySeconds` (5–86 400), `summaryEverySeconds`
  (10–86 400). Возвращает ID (`sch_` и 8 hex), город, оба интервала и время первого опроса и первой
  сводки в ISO UTC. Первые сроки: `createdAt + интервал`.
- `get_weather_summary` — ровно один из параметров `scheduleId` или `city`. Возвращает сохранённый Markdown
  сводки без повторной генерации. Если сводки ещё нет — сообщает время ближайшей публикации.
  Город сопоставляется в два шага: сначала точное совпадение строки (регистр и пробелы не различаются), иначе
  совпадение названия без уточнения после запятой — в обе стороны, так «Новосибирск» находит расписание
  «Новосибирск, Россия» и наоборот, — или имени места, которое вернул Open‑Meteo при закреплении точки.
  Другие словоформы («Новосибирске») не сопоставляются. Несколько подходящих расписаний — возвращаются их ID
  и города для выбора, активные предпочтительнее отменённых. Если подходящих нет, в ответе перечислены
  существующие расписания (не более 10, активные первыми), чтобы модель назвала их пользователю.
- `cancel_weather_schedule` — `scheduleId`. Прекращает будущие запуски, сохраняет историю и сводку.

Результаты содержат текст (Markdown) и `structuredContent` со статусом (`found`, `no_summary`,
`ambiguous`, `not_found` для чтения).

### Служебные операции worker

`worker_start` занимает единственное право worker на базу (`started` или `already_running`); остальные
операции без него отклоняются. `worker_get_due` возвращает наступившие сроки и ближайший срок;
`worker_record_poll` записывает успех или причину ошибки и назначает следующий срок опроса;
`worker_get_history` — опросы за период с включёнными границами; `worker_publish_summary` сохраняет готовый
Markdown; `worker_record_summary_failure` фиксирует причину, сохраняя прежнюю сводку.

## Хранилище

SQLite (`node:sqlite`, режим WAL, `busy_timeout` 5 с, короткие транзакции `BEGIN IMMEDIATE`). Таблицы:

- `schedules` — ID, город, оба интервала, оба следующих срока, закреплённая точка (широта, долгота и имя
  места из первого успешного опроса; имя участвует в сопоставлении города при чтении), время отмены, последняя ошибка публикации;
- `polls` — каждый опрос: время запроса, успех или причина ошибки, время наблюдения в UTC и показатели;
- `summaries` — каждая опубликованная сводка с периодом и числом уникальных наблюдений; читается последняя.

Геокодирование, вернувшее для расписания другую точку, чем первый успех, записывается как ошибка опроса.
База открывается при первом обращении, а не при старте процесса: клиент в режиме `auto` сначала запускает
пробный процесс, который не должен создавать файлы.

## Сроки

После опроса или публикации следующий срок равен `срок + интервал`, если он ещё в будущем; иначе — момент
фактического запуска `+ интервал`. После простоя просроченный опрос и просроченная сводка выполняются по одному
разу, цикл догоняющих запусков не создаётся; пропущенные периоды не превращаются в измерения.
Ошибка публикации тоже сдвигает срок: повторный платный запрос к модели сразу не выполняется.

## Единственный worker

Блокировка — эксклюзивная транзакция SQLite на файле `<база>.lock` рядом с базой (путь строится от реального
каталога). ОС снимает её при любом завершении процесса, поэтому устаревших блокировок нет: после штатной
остановки, `SIGKILL` или сбоя новый worker запускается без ручной очистки. Файл `.lock` при этом остаётся
на диске пустым.

## Отчёты

Host передаёт готовый Markdown. Сервер сохраняет его в SQLite, затем заменяет `<reports-dir>/<ID>.md` через
временный файл и rename. Атомарности между SQLite и файловой системой нет: отсутствующая или отличающаяся
копия `.md` восстанавливается из SQLite при чтении и публикации, а `.md` никогда не читается как данные.
После очистки базы оставшиеся `.md` не выдаются как актуальные.

## Ограничения

Нет запуска по расписанию вне worker, автозапуска, повторов опроса и сводки, уведомлений. История опросов не
очищается. За сутки при интервале 10 секунд worker читает до 8 640 строк истории для каждой сводки — интервал
10 секунд служит демонстрации; для постоянного сбора разумно около 15 минут.

## Запуск и проверка

```sh
npm run dev --workspace @mcp-lab/scheduler-server -- --db "$PWD/.local/scheduler.sqlite" --reports-dir "$PWD/.local/reports"
```

Тесты (`src/tests`) не используют внешние API: сервис и SQLite во временных каталогах с управляемыми часами,
протокол на in-memory transport, процессные тесты запускают настоящий `src/app/main.ts` по stdio (два
worker-процесса, `SIGKILL`, параллельные записи, `--ignore-sigint`). Сборка проверяется в `tooling/build.ts`.
